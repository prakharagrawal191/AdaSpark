# 3. Background and Literature Review

## 3.1 Apache Spark and its optimization surface

Modern analytics descends from MapReduce, which made batch processing fault-tolerant but forced every job through disk [35][36]. Resilient Distributed Datasets removed that bottleneck with in-memory lineage-based recovery, establishing Spark as the unified engine for batch, SQL, streaming, and machine learning workloads [1]. Spark SQL then added declarative optimization through the Catalyst optimizer [2], and lakehouse storage (Delta Lake) brought transactions to cloud object stores [33]. Each layer reduced hand-tuning — except execution configuration, which remains an exposed, high-dimensional surface of roughly two hundred parameters.

Static tuners attack this surface offline. Starfish pioneered self-tuning for MapReduce-era stacks by profiling jobs and searching configuration spaces automatically [6]. OtterTune transferred the idea to databases with Gaussian-process models over prior tuning sessions [7], and CDBTune/QTune brought deep-RL-flavoured tuning to database knobs [8][31]. For scheduling rather than configuration, Decima learns cluster scheduling policies with graph neural networks and RL [9]. Spark itself ships Adaptive Query Execution, which adjusts partitions and join strategies at runtime from observed statistics [34]. The residual gap AdaSpark targets is narrow: per-job execution-configuration selection (shuffle partitions × parallelism) by a sample-efficient online learner, complementing rather than replacing AQE.

## 3.2 Reinforcement learning for systems decisions

Reinforcement learning formalizes sequential decision-making as states, actions, and rewards optimized by a policy [3]. Tabular Q-learning converges under standard conditions for small discrete spaces [4], which matches a 12-action configuration grid exactly. Deep variants (DQN [38], policy gradients such as PPO [39], actor-critic methods such as DDPG [37]) handle large continuous spaces but demand thousands of training episodes and substantial compute — precisely the cost profile a practical tuning loop cannot afford. AdaSpark therefore uses ε-greedy tabular Q-learning in bandit mode (γ = 0, i.e. a contextual bandit; multi-step learning was gated off), deliberately trading representational power for sample efficiency inside a 500-execution budget. The autonomic-computing vision of self-managing systems [5] and its MAPE-K control pattern [32] provide the architectural frame: monitor, analyze, plan, and execute around a shared knowledge base.

## 3.3 Rigorous performance measurement

A tuning claim is only as credible as its measurement. Georges et al. established statistically rigorous Java performance evaluation with confidence intervals over repetitions [11]; Kalibera and Jones gave the definitive methodology for choosing repetition counts under independence assumptions [12]. The independence assumption is exactly what breaks in practice: Mytkowicz et al. showed how easily measurement bias produces wrong data without any obvious error [14], and profiler studies show how inaccuracy compounds it [15][26]. Cloud and shared-host variability further widen the problem (predictability studies [20], microbenchmarking in the cloud [19], repeatability methods [17], duet benchmarking [18], reproducibility principles [24]), with big-data-specific evidence from networked-system studies [21][22] and analytics-framework analyses [23]. Warmup non-stationarity [13][25] and noisy-environment benchmarking practice [16] complete the picture: repetitions of the same job are serially dependent, regime-structured episodes — which is precisely what AdaSpark's own 4,842-run study measures (lag-1 autocorrelation +0.58…+0.89 across 21 series; contention episodes to 75% dispersion).

## 3.4 Monitoring-overhead evidence

Continuous monitoring is the sensor of any MAPE-K loop, so its cost must be quantified rather than assumed. Kieker provides the canonical application-monitoring framework reference [27]; recent ICPE work attacks minimal-overhead monitoring directly [28] and compares instrumentation-framework overheads head-to-head [29]; Google-wide continuous profiling demonstrates production feasibility at data-center scale [30]. Spark's own monitoring surface (metrics system, event logs, listener bus) is documented by the project [10]. Against this background, no peer-reviewed controlled study was found measuring sampling-based system monitoring plus event logging in Spark against a stated budget with interval adjudication — the specific measurement this project contributes. The search covered the venues above over 2020–2025; the claim is scoped to that search and stated so it can be checked.

The benchmarking-threats literature, finally, reads as a checklist this project was graded against: run-to-run variability and warmup [11][13][19][25], profiler and measurement bias [14][15][26], cloud variability and reproducibility [17][18][20][21][22][24], and analytics performance [23]. Each threat maps to a concrete control in Sections VI–XII (seeded determinism, per-record validity, sealed evaluation, frozen analysis code), so related work functions here as the audit standard the project holds itself to — the same standard that produced the negative findings reported in Section XV.

## 3.5 Configuration auto-tuning and learned optimizers

Configuration tuning for Spark-class engines is now a research area of its own. Spark SQL execution time varies significantly with configuration, which motivates accelerated configuration search for SQL applications [50]. Generative adversarial models have been used to explore the high-dimensional, interacting parameter spaces of Spark and Storm [51], and auto-tuning frameworks for parallel programs handle interdependent tuning parameters explicitly [52]. For recurring jobs, CausalConf makes tuning aware of input data size [53], while DeepCAT+ reports that online deep-RL tuning beats search- and model-based tuners but carries a heavy online tuning cost, which it reduces with prioritized replay and transfer [54]. Neighbouring work optimizes other levers of the same engine: executor allocation for data locality [55], intermediate-data partitioning against skew [45], RL-based straggler identification on heterogeneous Spark clusters [56], and learned plan selection for Spark SQL [57].

Database tuning travelled the same road earlier and supplies the clearest cautions. A survey of automatic knob tuning catalogues hundreds of knobs, few of which matter for a given workload, under expensive evaluation [58], and DOT responds with dynamic knob selection and online sampling [59]. Holon tunes knobs, hints and indexes jointly instead of one configuration space at a time [60]. Learned optimizers produce strong average plans [61] yet regress unpredictably on some queries [62], do not always behave as their designers expect [63], and need workload models that track shifting distributions [47]. Most pertinently, ML tuners had been evaluated on synthetic workloads with limited tuning opportunities, and only a dedicated study on an enterprise Oracle deployment with a real workload trace established a 45% improvement over enterprise-grade configurations in production [64]. That is the same move this report makes in Section XV: an earlier descriptive result is re-tested under stricter, pre-registered conditions before it is believed.

## 3.6 Reinforcement learning for scheduling, resource allocation and autoscaling

RL is now a standard tool for resource decisions. Graph-based deep RL schedules tasks on heterogeneous cloud resources [65], DeepHCM extends RL job scheduling to heterogeneous, load-aware clusters and reduces slowdown under heavy load [66], and representation learning combined with RL schedules edge tasks for energy [67]. Cloud–fog task schedulers [68], workflow schedulers that duplicate tasks to cut completion time and cost for big-data pipelines [69], and throughput-maximizing operator placement for Storm [70] show the breadth of the problem. RL also allocates memory on industrial edge controllers [71] and cache space among tenants with an online model-based learner [72], and ReinFog packages DRL resource management as a modular edge–cloud framework [73]. One strand bears directly on AdaSpark's budget constraint: offline RL learns dispatching rules from historical data precisely because online RL is sample-inefficient and needs simulators that are impractical to build [74], while hierarchical multi-policy DRL coordinates multi-objective manufacturing schedules [75].

Autoscaling is the closest operational relative of configuration tuning. RL-based autoscalers learn multi-metric thresholds for microservices [76], recurrent RL scales serverless functions under fluctuating load [77], and ASTRA transfers simulator-trained autoscaling policies to real systems adversarially [78]. Non-RL designs remain strong: QoS-driven microservice autoscaling [79], supervised predictive scaling that accounts for VM performance that varies over time [80], multi-loop controllers [81], adaptive provisioning across pricing models [82], and decentralized, quasi-continuous scaling that outperforms centralized interval-based autoscalers [83]. The lesson for AdaSpark is that learned controllers must beat strong static and rule-based comparators, not defaults alone.

## 3.7 Self-adaptive systems, DataOps and MLOps

The self-adaptive-systems community has systematically studied where machine learning fits in the feedback loop [84][85]. It uses learning to reduce large adaptation spaces before analysis [86] and couples ML components with probabilistic model checking so adaptation tactics such as retraining are chosen deliberately [87]. Hyperparameter-optimization research contributes multi-objective search methods [88] and Bayesian optimization for configuration selection [89]. Operational practice frames how such loops are run: MLOps defines the roles, components and workflows for taking ML into production [48], DataOps reviews identify integration, delivery and governance obstacles in large enterprises [49], data-quality discovery tools support non-expert data workers [90], and ML lineage connects model development and operations into an auditable record [91]. AdaSpark's manifests, sealed splits and decision log are a small-scale instance of exactly this operational discipline.
