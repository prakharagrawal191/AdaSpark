# 5. Reinforcement Learning-Driven Spark Architecture

AdaSpark implements Candidate C — hybrid offline-init plus bounded online adaptation — selected over pure-offline and pure-online alternatives against eight criteria and then frozen as twelve components with fourteen interfaces (Figure 6, the core figure of this report). The architecture is a MAPE-K loop made concrete: the monitoring layer (COMP-SPARK) observes; the RL formulation (state encoder, environment, agent, reward) analyzes and plans; the runner executes the chosen configuration; and the knowledge base (Q-tables, T_ref calibrations, manifests, policy store) persists everything learned [5][32].

Placing a learner inside MAPE-K is a well-studied pattern: reviews of machine learning in self-adaptive systems find learning concentrated in the analysis and planning stages, exactly where AdaSpark's agent sits [84], and recent work adds formal checks around the learned component so that adaptation tactics are chosen deliberately [87]. Comparable DRL frameworks for edge–cloud resource management package monitoring, learning and actuation as separate modules [73], and model-based online RL has been used where each decision is costly to evaluate, such as cache allocation [72]. AdaSpark differs in scale and emphasis: a deliberately small tabular learner, a fixed decision boundary (one configuration per run), and governance components that are first-class parts of the architecture rather than wrappers around it.

The data plane is deliberately boring: standard Spark jobs on a fixed single-node backend (PySpark 3.5.9, Java 17), so that all intelligence lives in the decision plane. The decision plane centers on a 30-state representation (workload class × size bin × feedback bin), a 12-action grid (shuffle partitions {16, 32, 64, 128} × parallelism {local-2, local-4, local-8}), and the frozen R3 reward (time improvement + task balance − spill waste − failure penalty; Section 7, Equation 1). Offline initialization (Q0) calibrates the agent from the EXP-002 sensitivity grid before any online learning, so the first policy is already informed; the online loop (Figure 7) then refines it with ε-greedy tabular Q-learning (α = 0.2, γ = 0.0 bandit mode) inside the 500-execution guard.

Three structural properties matter more than any single result. First, failure is a first-class observation: a failed episode returns reward −1 and still updates the learner, so the agent learns to avoid pathological configurations rather than ignoring them. Second, the train/validation/test boundary is a code-enforced authorization boundary, not a convention — the Day-31 gate verifies it with 36 checks. Third, scope reduction is pre-designed (Plan B via config selectors: drop multi-step, shrink ablations, narrow the action space) rather than improvised, which is why the Day-30 decision to disable multi-step learning consumed a planned scope rung instead of causing a crisis.

The twelve frozen components span the full pipeline: session management, configuration handling, and job running (COMP-SPARK); deterministic data generation, workload families with registry/resolver, and the monitoring stack with metrics merge and validation; the RL core of state encoder, action mapper, reward calculator, environment with T_ref store, and tabular agent with Q0 and policy store; and the training loop, execution cache, evaluation harness with frozen test identity, and baseline strategies. Fourteen interfaces connect them, and twelve JSON-serializable data contracts govern every handoff with determinism rules — seeded manifests in, metrics out, no hidden channels. Architectural invariants hold the design together: single-node execution, seeded manifests, config-driven behavior, the 12-action bound, T_ref-gated rewards, the ≤500 execution guard, deterministic caching, identical-baseline protocols, AQE control, a frozen test set, ±5% reproduction targets, and Plan-B recoverability — with explicit exclusions (no cluster or Kubernetes, no deep RL, no GPU path) keeping the scope honest. Experiment compatibility was verified per component: every experiment from EXP-001 through EXP-012 (plus 005b) executes against these contracts unchanged, and the four architecture diagrams (system, training loop, execution pipeline, data/control flow) are generated from the same source so documentation cannot drift from implementation.
