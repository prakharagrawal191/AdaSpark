# 1. Introduction

Big-data analytics has evolved from hand-written MapReduce jobs over batch windows to declarative, interactive, and streaming computation on unified engines. Apache Spark became the de-facto standard for this evolution by combining in-memory execution, a rich SQL and DataFrame API, and a growing set of runtime adaptations, most notably Adaptive Query Execution (AQE), which adjusts shuffle partitions and join strategies at runtime [1][2]. Each step in this evolution (Figure 1) removed one class of manual effort — yet one class remains stubbornly manual: choosing the execution configuration under which a job runs.

A Spark application exposes on the order of two hundred configuration parameters, from `spark.sql.shuffle.partitions` to executor memory, serialization, and spill thresholds. Defaults are compromise values; optimal values depend on workload composition (joins vs aggregations vs sorts), data scale, and skew — all of which drift over a workload's lifetime. In practice, organizations respond with static tuning: an expert studies a workload, fixes a configuration, and moves on until performance visibly degrades. Rule-based heuristics (e.g., scaling partitions with input size) improve on defaults but encode assumptions that break silently, as this project's own heuristic did — collapsing byte-identically onto the static tuning at the studied data volumes. The structural problem is that configuration selection is an open loop: nothing observes the outcome and feeds it back into the next decision.

Reinforcement learning offers a principled way to close that loop. An RL agent learns a policy mapping observed state to configuration actions, optimized against measured reward, improving with experience rather than degrading with drift. Unlike offline Bayesian-optimization tuners that emit one static configuration, an online RL loop keeps adapting; unlike deep-RL proposals that demand thousands of training executions and cluster-scale resources, a tabular agent with offline initialization can operate inside a few hundred executions — a budget a single team can afford. This report's central proposition is therefore narrow and testable rather than visionary: that Spark execution-configuration selection can be made self-adaptive with sample-efficient RL inside a practical budget, and that the benefit — if any — can be measured against appropriate baselines with statistical validity.

AdaSpark realizes this proposition as a layered self-adaptive analytics ecosystem (Figure 2). Workloads execute on a standard Spark deployment; a monitoring layer instruments every run (system metrics plus Spark event logs); the RL optimization layer maps workload context and runtime feedback to configuration decisions; resource-scheduling and self-tuning layers enact those decisions within governed bounds; and explainability and governance layers keep every decision traceable. The MAPE-K loop (Monitor–Analyze–Plan–Execute–Knowledge) is not a decorative reference here but the implemented control structure: each phase corresponds to named components with frozen contracts.

The remainder of this report is organized as follows. Section 2 formalizes the problem and research gaps; Section 3 surveys the literature; Section 4 derives system requirements; Sections 5–12 present the architecture layer by layer, with the RL-driven design (Section 5) as the core figure; Sections 13–14 describe the experimental setup and metrics; Sections 15–17 report results, comparative analysis, and trustworthiness assessment — including negative findings; Section 18 maps the framework to industry use cases; Section 19 assesses business impact; Section 20 discusses challenges and limitations honestly; Section 21 charts future research; and Section 22 concludes. All measured claims trace to committed project artifacts; prospective material is labelled as such.

Two properties of this report deserve notice up front because they shape everything that follows. First, negative results are first-class content: the failed policy-agreement gate, the undecided main hypotheses, the falsified repetition model, and the unexecuted AQE condition each receive the same evidentiary treatment as the positive findings — with numbers, mechanisms, and consequences. Second, governance is presented as engineering rather than administration: budget guards, test seals, and decision logs are code and artifact properties with test suites, reported alongside the learning results because they are what make the learning results believable. Readers primarily interested in the framework can focus on Sections 5–12; readers primarily interested in what was actually measured can read Sections 15–17 standalone.
